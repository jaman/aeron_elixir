Strengths

What the BEAM brings to Aeron

01 / PUBLISH FROM ANY PROCESS

Any number of processes can publish to the same stream at once. Each message claims its own space in the shared buffer, so nobody waits on a lock or queues behind anyone else.

02 / NOTHING IN THE MIDDLE

Publishing and polling happen right inside the process that calls them. No server process relays your messages, so one busy process never holds up the rest.

03 / BATCHES WHEN YOU NEED SPEED

Send a whole list in one call with publish_list/2, or read many messages at once with poll_batch/2. BatchPublisher gathers messages from many processes and sends them together, without making any of them wait.

04 / SEND WHAT YOU ALREADY HAVE

Pass a binary or iodata as it is; nothing has to be joined up first. Large messages are split on send and put back together on receive for you.

05 / THE DRIVER COMES WITH IT

The Aeron media driver is built with the library and runs under your application's supervisor, with nothing to install or configure. Point AERON_DIR at a driver that is already running to share it instead.

06 / TALKS TO EVERY AERON CLIENT

It speaks the same protocol as Aeron's Java, C and C++ clients and pyaeron, so Elixir services share streams with them on one machine or across the network.

Elixir API

Aeron's model, in ordinary Elixir

Tagged tuples for every outcome, iodata for every payload, a handle any process can hold.

01 / PUBLISH

Offer with back-pressure you can see

  • publish/2 retries until the client's driver timeout; try_publish/2 makes one attempt.
  • Returns {:ok, position} or :back_pressured, :not_connected, :admin_action, :closed.
alias AeronElixir, as: AE

{:ok, client} = AE.start_link()

channel = AE.ChannelUri.ipc(alias: "orders", term_length: 16_777_216)
{:ok, publication} = AE.add_publication(client, channel, 1001)
:ok = AE.await_connected(publication)

{:ok, _position} = AE.publish(publication, ["order:", "42"])

02 / SUBSCRIBE

Poll whole messages, never fragments

  • poll/3 and controlled_poll/3 take a handler; :continue, :commit, :break, :abort steer consumption.
  • Get a callback whenever a publisher joins or leaves the stream.
{:ok, subscription} =
  AE.add_subscription(client, channel, 1001,
    available_image: &IO.inspect(&1, label: "joined")
  )

AE.poll(subscription, 10, fn payload, header ->
  IO.inspect({AE.Header.session_id(header), payload})
end)

03 / BATCH

Cross into native code once per batch

  • Keep a handle so each call skips looking up the publication.
  • BatchPublisher never blocks the caller and drops nothing.
{:ok, handle} = AE.publication_handle(publication)
{:ok, 3} = AE.publish_list(handle, ["a", "b", "c"])
{:ok, 3, ["a", "b", "c"]} = AE.poll_batch(subscription, 64)

{:ok, batcher} = AE.BatchPublisher.start_link(publication: publication)
:ok = AE.BatchPublisher.publish(batcher, "fire and forget")

How it works

From one process to another, through shared memory

01 / PUBLISHERS

A process calls publish. The message is written into a buffer in shared memory and marked complete only once every byte is in place, so a reader never sees half a message.

02 / MEDIA DRIVER

A separate program that owns the buffers. On one machine it keeps publishers from getting too far ahead of the slowest reader; across machines it sends and receives the messages over UDP.

03 / SUBSCRIBERS

A process calls poll. It reads every complete message since its last poll, joins split messages back together and returns them as ordinary binaries.

Messages arrive as ordinary binaries

Each message is copied out of shared memory, so it is safe to keep and pass around. The messages from one poll share a single copy; if you hold on to one long after the poll, call :binary.copy/1 on it so the rest can be freed.

Who may call what

Any number of processes can publish to the same publication at once. Only one process should poll a given subscription at a time.

The media driver

Built in, supervised, and honest when it goes away

The Aeron C media driver is compiled with the library and started under your application's supervisor. Nothing needs installing; one setting points it at a driver you already run instead.

SettingWhat happens
Nothing set The bundled driver starts with your application, in a directory private to it, and is restarted if it exits.
AERON_DIR or config :aeron_elixir, aeron_dir: Connect to the driver something else runs there, such as a host service or another application. Nothing is started.
driver: :embedded with a directory This application runs the driver at a shared location for other programs on the host to use.
binary: path Launch another aeronmd instead of the bundled one, still supervised.

When the driver goes away

The client follows the same contract as Aeron's Java and C clients. If the driver shuts down, stops heartbeating for the driver timeout, or reports that the client timed out, every publication and subscription is closed: publishing returns {:error, :closed}, polling reads nothing, and your image-unavailable callbacks run. The check runs in the client's own process, never on the publish or poll path.

Supervision brings it back

The client process exits with the reason, such as {:shutdown, :driver_timeout}. Put the processes that own publications after it in a :rest_for_one supervisor: they restart in order, wait for the driver, and add their publications again. 

children = [
  {AeronElixir, name: MyApp.Aeron},
  MyApp.OrderPublisher
]

Supervisor.start_link(children, strategy: :rest_for_one)
aeron_elixir Aeron, without leaving the BEAM.
